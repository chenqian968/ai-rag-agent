# 项目答辩讲稿

**项目**：AI 知识库问答 Agent（ai-rag-agent）
**岗位方向**：大模型应用 / AI Agent 开发工程师
**准备时间建议**：面试前通读 2~3 遍，重点背熟「1 分钟陈述」和「技术难点」两部分。

---

## 一、1 分钟电梯陈述（自我介绍时用）

> 我独立完成了一个基于 **RAG + AI Agent** 的垂直领域智能问答系统。它能让用户上传私有文档（PDF、Word、Markdown、TXT）建立专属知识库，然后用自然语言提问，系统会检索相关内容并**带引用来源地作答**，有效抑制大模型幻觉。
>
> 技术上我用 **LangChain** 做 RAG 检索链，用 **LangGraph** 实现 ReAct 智能体——让 AI 能自主决定「要不要查知识库、查几次、要不要计算」，而不是固定走「检索→生成」的流水线。后端用 FastAPI，前端是原生网页，最后用 Docker 打包部署。
>
> 这个项目最有价值的地方，是我在调优检索效果时踩了不少坑，比如**中文分词的检索召回问题**、**多领域文档混库时的向量噪音问题**，最后都通过混合检索策略解决了。

## 二、3 分钟项目介绍（正式讲解用）

### 1. 项目是什么（30 秒）

一句话：**一个能"喂文档、问答案、有引用"的私有知识库问答 Agent。**

解决的核心痛点：大模型有两个问题——① 不知道你的私有资料；② 会一本正经地胡说八道（幻觉）。RAG 解决"不知道私有资料"，引用溯源解决"胡说八道"。

### 2. 技术架构（1 分钟）

分四层：
- **表示层**：原生网页 + 命令行；
- **应用层**：FastAPI 提供 4 个接口（对话、上传、清空、健康检查）；
- **Agent 编排层**：LangGraph 实现 ReAct 循环，两个工具（知识检索、数学计算）；
- **数据层**：Chroma 向量库，Embedding 用硅基流动的 bge-m3。

### 3. 核心流程（1 分钟）

一次提问的完整链路：
1. 用户提问 → FastAPI 接收；
2. Agent 判断「要不要调工具」；
3. 若涉及知识库 → 调用检索工具，走**混合检索**（语义相似度 + 关键词兜底）；
4. 把检索到的文本块拼进 Prompt，要求模型只依据资料作答并标注 `[资料N]`；
5. 返回带引用的答案。

### 4. 我的收获（30 秒）

最大的收获不是"跑通了"，而是**理解了检索质量是 RAG 的命门**——向量检索不是万能的，专业术语、中文分词、多领域混库都会导致召回失败，需要针对性优化。

## 三、5 分钟详细讲解（技术深挖用）

### 模块拆解

| 模块 | 技术 | 面试官可能追问的点 |
|---|---|---|
| 文档加载 | TextLoader / PyPDFLoader / Docx2txtLoader | 为什么 .md 不用重型库？ |
| 分块 | RecursiveCharacterTextSplitter | chunk_size 怎么定的？overlap 作用？ |
| 向量化 | bge-m3（1024 维） | 为什么选它？ |
| 向量库 | Chroma | 为什么不用 Milvus？ |
| 检索 | 混合检索（语义+关键词） | 纯向量检索的短板？ |
| Agent | LangGraph ReAct | 为什么用 LangGraph 不用手写循环？ |
| 工具调用 | DeepSeek Function Calling | bind_tools 解决了什么？ |

### 三个真实踩坑（重点讲，这是你的差异化优势）

**坑 1：换知识库后 Agent 不检索新文档**
- 现象：上传大数据文档，问大数据问题，AI 凭记忆答、没查库。
- 根因：系统提示词写死了旧主题「股票投资」，Agent 误判「不相关」。
- 教训：检索策略要和领域预设解耦。

**坑 2：中文查询检索不到目标文档**
- 现象：问「小个子显高的搭配思路」，召回的却是股票、大数据块。
- 根因：中文分词错误——「去停用字拼串」把「小个子显高的搭配思路」粘成无意义的「小子显高搭配路」。
- 解决：改用 n-gram 滑动切词 + 关键词命中数重排。

**坑 3：多领域混库的向量噪音**
- 现象：股票、大数据、穿搭三个领域混在一个向量库，纯向量相似度被领域间噪音稀释。
- 解决：混合检索，关键词字面命中优先。

## 四、高频面试问题与回答话术

### Q1：什么是 RAG？为什么要用？

> RAG 是检索增强生成，核心思路是在回答前先"查资料"。大模型有两个短板：一是训练数据有截止日期、不知道你的私有数据；二是会幻觉。RAG 通过"先检索相关文档片段，再让模型基于这些片段作答"，既注入了私有知识，又通过约束"只依据资料作答"抑制幻觉。我的项目里还加了引用标注，让答案可溯源。

### Q2：RAG 和微调（Fine-tuning）的区别？

> 简单说，RAG 是"开卷考试"（查资料回答），微调是"背书"（把知识写进模型权重）。RAG 的优点是知识更新快（换文档就行）、可溯源、成本低；缺点是检索质量是关键瓶颈。微调适合让模型学会某种风格或能力，但知识更新要重新训练。我的场景是"用户随时上传新文档"，所以 RAG 更合适。

### Q3：向量检索为什么不准？你怎么优化？

> 三个原因：① 专业术语/缩写在向量空间里容易被稀释；② 中文分词不当导致字面匹配失败；③ 多领域混库时领域间噪音干扰。我的优化：混合检索——语义检索 + 关键词兜底，用 n-gram 切词提取实义词，按关键词命中数重排。效果是原来召不回的中文问题都能命中了。

### Q4：LangGraph 相比手写 while 循环有什么优势？

> 手写循环也能实现 Agent，但 LangGraph 把流程建模成"图"——节点是动作、边是流转条件。优势：① 可观测，每一步状态清晰；② 可扩展，加节点/工具方便；③ 支持状态持久化和检查点，便于调试。而且面试时能体现你对主流 Agent 框架的理解。

### Q5：Function Calling 你遇到过什么坑？

> 早期手写 OpenAI 的 Function Calling 序列化，`type` 字段填错（应该是 `function` 不是 `tool_call`）导致调用失败。后来改用 LangChain 的 `bind_tools`，让框架自动生成 JSON Schema 并处理结果回传，问题解决。教训是不要重复造轮子，用成熟框架的封装。

### Q6：chunk_size 怎么选？有什么权衡？

> 我用 300 字符 + 30 重叠。块太大检索粒度粗、容易把多个知识点混一起稀释语义；块太小上下文不完整、可能把关键信息切断。overlap 是让相邻块保留重叠，避免切分点正好切断关键定义。具体值要结合文档特点实验调优。

### Q7：Embedding 为什么选 bge-m3？

> 两个原因：① 中文语义效果好，bge 系列是中文榜单靠前的开源模型；② 硅基流动提供 OpenAI 兼容接口，接入成本低。1024 维在效果和存储开销之间平衡得不错。

### Q8：如果知识库很大（百万级），你的方案怎么扩展？

> 当前是本地 Chroma、全量取回重排，适合演示。生产化要做几件事：① 向量库换 Milvus 或 pgvector 支持海量数据；② 检索用 ANN 近似最近邻（如 HNSW 索引），不能全量取回；③ 关键词兜底改用 BM25 等倒排索引做混合检索（RAG 里的 Hybrid Search）；④ 引入 rerank 模型对召回结果精排。

### Q9：怎么评估 RAG 效果？

> 我用了"样例问题集"做召回率测试——准备一批有标准答案的问题，逐个看检索结果里有没有含答案的块，统计命中率。我调优后样例问题从召回不准到 9/9 全通过。生产上还可以用 RAGAS 这类框架做 faithfulness（忠实度）和 answer relevancy（相关性）评估。

### Q10：这个项目如果重做，你会怎么改进？

> ① 引入 rerank 精排，提升排序质量；② 支持多轮检索改写（query rewriting），把口语化问题改写成更适合检索的查询；③ 加记忆管理，对话长了要做历史压缩或摘要；④ 做流式响应和更完整的前端体验；⑤ 用 Docker + 云服务真正上线，而不是本地演示。

## 五、STAR 法则话术模板（行为面试用）

**S（情境）**：作为求职准备，我需要一个能体现大模型应用开发能力的项目。

**T（任务）**：从零搭建一个 RAG + Agent 的私有知识库问答系统，四周完成。

**A（行动）**：
- 第一周搭环境、调通 LLM 调用；
- 第二周实现 RAG（分块、向量化、检索）；
- 第三周升级为 Agent（工具调用、多轮记忆）；
- 第四周产品化（FastAPI、网页、Docker）；
- 全程记录踩坑，优化检索召回。

**R（结果）**：交付了一个可演示的完整产品，检索准确率从"召不回"提升到样例问题全通过，沉淀了技术博客和软件工程文档四件套。
